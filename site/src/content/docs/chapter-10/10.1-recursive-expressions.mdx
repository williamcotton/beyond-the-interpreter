<p className="book-subtitle">Chapter 10 · Representing Expressions</p>

Our scanner can recognize every token in `(123)`: an opening parenthesis,
a number, and a closing parenthesis. The result is a flat sequence. What
would it mean to represent the expression inside those parentheses as one
thing?

A grouping contains another expression. That inner expression might be a
number, or it might be another grouping. We need a representation whose
parts can contain more values of the same type.

Start from [Section 9.5](/chapter-9/9.5-editor-ci/). Return to your **Rust
workspace directory**, the one containing the workspace `Cargo.toml` and
`crates/`. If your terminal is still in `editors/vscode/`, run:

```sh
cd ../..
```

Paths below begin with `rlox/` to identify files in this book's repository;
commands run from the Rust workspace itself. We'll add an expression module
to the existing `rlox-syntax` crate and construct its values by hand.

## See the expression inside the group

Think of a number as a leaf: it has no expression children. A grouping has
one child. For `(123)`, the tree is:

```text title="Expression tree for (123)"
Grouping
  │ contains
  ▼
Number: 123
```

The root is the grouping; its child is the number. Another pair of
parentheses adds another grouping above it. We can describe `((123))` with
the same two kinds of node:

```text title="Expression tree for ((123))"
Grouping
  │ contains
  ▼
Grouping
  │ contains
  ▼
Number: 123
```

This is the beginning of an **abstract syntax tree**, or AST. It records
expression structure. We represent a pair of parentheses with a grouping
node rather than storing two punctuation children. Our scanner and source
text still retain the original spelling, ranges, whitespace and punctuation;
this small tree doesn't attempt to preserve all of those details.

[Crafting Interpreters introduces syntax trees](https://craftinginterpreters.com/representing-code.html#implementing-syntax-trees)
for the same reason: nesting and relationships become explicit. We'll use
Rust's enums to express the alternatives.

## Try putting an expression inside itself

Our existing `SyntaxKind` enum names token categories. An expression enum
needs to carry data too. `Number(f64)` means “this expression is a number,
and here is its value.” `f64` is Rust's 64-bit floating-point type; the
literal `123.0` has that type in this constructor.

A grouping seems as though it could carry another `Expr` directly. Let's
try that first and see what Rust needs from us.

**This first definition is an intentional compile failure.** Create
**`rlox/crates/syntax/src/expr.rs`** with this complete initial content:

```rust title="rlox/crates/syntax/src/expr.rs · intentional recursive-size error"
#[derive(Debug)]
pub enum Expr {
    Number(f64),
    Grouping(Expr),
}
```

`#[derive(Debug)]` asks Rust to generate a diagnostic representation, so we
can inspect these values later. It doesn't evaluate a Lox expression.
The `pub` enum will be usable by another crate or by a Cargo example.
Its variants belong to it: we construct a number as `Expr::Number(123.0)`.
The Rust Book explains [enum variants with associated data](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html#enum-values).

Rust also needs to know that this file is part of our library. At the top
of **`rlox/crates/syntax/src/lib.rs`**, add the module declaration before the
existing imports:

```diff title="rlox/crates/syntax/src/lib.rs · expose the expression module"
+pub mod expr;
+
 use logos::Logos;
```

`mod expr` makes Rust load the sibling `expr.rs` file; `pub` makes the
module accessible outside the library. Creating the file alone wouldn't
connect it to the crate. Complete both edits before checking:

```sh
cargo check -p rlox-syntax
```

The check should fail with **E0072**, reporting that the recursive type
`Expr` has infinite size. The compiler may also show related layout errors;
the recursive child is the problem to fix.

Rust needs a fixed size for an `Expr` value. Its number variant contains an
`f64`. But how much space should the grouping variant reserve for its
child? That child is also an `Expr`, so it needs enough space for a grouping
containing another `Expr`, and so on.

The trees we want are finite. The problem is that the type tries to reserve
space *inline* for any nesting depth. A number at the end of one particular
tree can't give every value of the type a fixed layout. See Rust's
[E0072 explanation](https://doc.rust-lang.org/error_codes/E0072.html).

## Give the child its own allocation

A `Box<Expr>` owns an expression stored in a separate heap allocation. The
box itself has a known size, so the grouping variant can store it without
embedding the child's entire layout.

Change just the grouping payload in **`expr.rs`**:

```diff title="rlox/crates/syntax/src/expr.rs · put indirection before the child"
 #[derive(Debug)]
 pub enum Expr {
     Number(f64),
-    Grouping(Expr),
+    Grouping(Box<Expr>),
 }
```

Here is the distinction in layout. The arrows describe containment or
ownership, not an exact byte layout:

```text title="Direct embedding versus an owned pointer"
Direct child: layout cannot finish
  Expr → room for an entire Expr → room for an entire Expr → ...

Boxed child: each node has a finite layout
  Expr holding Grouping
    └─ Box pointer ──owns──▶ separate heap allocation: Expr
                              └─ if Grouping, another Box pointer
```

A node can still have another grouping as its child. That child lives in
another allocation instead of needing to fit inside its parent's storage.
The root value can live wherever its owner stores it; boxing a child doesn't
mean every value or every field has moved to the heap.

`Box<T>` is supplied by Rust's standard library and available without an
import. `Box::new(value)` moves a value into a new allocation and returns
its owning box. Dropping the box drops its child and releases that
allocation. With nested boxes, ownership continues down the tree. We don't
need manual deallocation or shared ownership for this structure.

The [Rust Book's recursive types with boxes](https://doc.rust-lang.org/book/ch15-01-box.html#enabling-recursive-types-with-boxes)
walks through this size problem in more detail.

Run the same check again:

```sh
cargo check -p rlox-syntax
```

It should now succeed. We have a recursive type with a finite layout.

## Construct and inspect a small tree

Let's build the trees from our diagrams. Cargo examples give us a small
executable that can use the library without adding a CLI subcommand.
Create its directory from the Rust workspace:

```sh
mkdir -p crates/syntax/examples
```

Create **`rlox/crates/syntax/examples/expression_shape.rs`** with this
complete content:

```rust title="rlox/crates/syntax/examples/expression_shape.rs"
use rlox_syntax::expr::Expr;

fn main() {
    let number = Expr::Number(123.0);
    println!("number: {number:?}");

    let grouped = Expr::Grouping(Box::new(number));
    println!("grouped: {grouped:?}");

    let nested = Expr::Grouping(Box::new(grouped));
    println!("nested: {nested:?}");
}
```

The library's package name is `rlox-syntax`; Rust import paths use the crate
name `rlox_syntax`. The rest of the path follows our public module and enum.

`Expr::Number(123.0)` is one leaf. `Box::new(number)` moves that leaf into
an allocation, and `Expr::Grouping(...)` makes a parent that owns the box.
The `number` binding can't be used after that move. We can move the resulting
`grouped` value into another box in exactly the same way.

The three `println!` calls happen before each value is moved onward. The
`:?` format uses the derived `Debug` implementation and borrows the value
for inspection. It doesn't consume it, so the subsequent move is allowed.
This is the first time we need ownership to connect syntax nodes; the
Rust Book's [ownership rules](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html#ownership-rules)
provide the broader model.

Run the example:

```sh
cargo run -p rlox-syntax --example expression_shape
```

After Cargo's build messages, expect:

```text title="Diagnostic views of the three expression values"
number: Number(123.0)
grouped: Grouping(Number(123.0))
nested: Grouping(Grouping(Number(123.0)))
```

The number is still the innermost leaf. Each construction adds one grouping
around it, matching the two diagrams. `Box` forwards debug formatting to its
child, so no `Box(...)` wrapper appears in this output. These are diagnostic
Rust views; we'll write a deliberate tree printer later in the chapter.

```sh
cargo fmt --all -- --check

```

The examples compile with `--all-targets`; running the example separately
checks the displayed observation. The scanner and CLI tests should continue

shape; it doesn't mean we've parsed any source yet.

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Token {
    pub kind: SyntaxKind,
    pub range: TextRange,
}

pub fn scan(source: &str) -> Vec<Token> {
    let mut tokens = Vec::new();

    for (result, span) in SyntaxKind::lexer(source).spanned() {
        let kind = match result {
            Ok(kind) => kind,
            Err(()) => SyntaxKind::Error,
        };
        let range = TextRange::new(TextSize(span.start), TextSize(span.end))
            .expect("Logos spans are ordered");

        tokens.push(Token { kind, range });
    }

    tokens
}
