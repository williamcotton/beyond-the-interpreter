The scanner can recognize `print`, but the digits in `print 123.45;` still
become errors. We need a `Number` kind that keeps the whole number spelling
together. The interesting boundary is the dot: when does it belong to a
number, and when should it remain a `Dot` token?

Start from [Section 7.3](/chapter-7/7.3-keywords/), with your terminal in
**`rlox/`**. All edits belong to **`rlox/crates/syntax/src/lib.rs`**.

## A decimal needs digits on both sides

Lox numbers begin with one or more ASCII digits. They may continue with a
literal dot and one or more additional digits. This follows the
[number scanning rule in Crafting Interpreters](https://craftinginterpreters.com/scanning.html#number-literals).
For `123.45`, the fractional part belongs to the number. For `123.`, the dot
has no following digit, so it stays separate. Likewise, `.5` starts with a dot,
not a number.

Here are the boundaries we want, with byte positions local to each source:

```text title="A dot joins a number only when followed by digits"
123.45
  Number  [0, 6)  "123.45"
123.
  Number  [0, 3)  "123"
  Dot     [3, 4)  "."
.5
  Dot     [0, 1)  "."
  Number  [1, 2)  "5"
1.2.3
  Number  [0, 3)  "1.2"
  Dot     [3, 4)  "."
  Number  [4, 5)  "3"
```

Recognizing these tokens doesn't make every example a valid expression.
Deciding how tokens fit together belongs to the parser.

## Describe the spelling in one rule

Inside `SyntaxKind`, insert these two lines **immediately before the existing
`#[regex(r"[A-Za-z_][A-Za-z0-9_]*")]` attribute on `Identifier`**:

```rust title="rlox/crates/syntax/src/lib.rs · insert before Identifier"
#[regex(r"[0-9]+(\.[0-9]+)?")]
Number,
```

The first `[0-9]+` requires at least one ASCII digit. The group
`(\.[0-9]+)` describes a literal dot followed by at least one digit, and the
final `?` makes that entire group optional. The `+` inside the group matters:
`123.` cannot satisfy the fractional part, so the number ends before the dot.

An unescaped `.` in a regex means any matching character; `\.` means the dot
itself. Rust's `r"..."` raw string passes that backslash through unchanged,
just as in our existing trivia rules. Logos's
[regular expression guidance](https://logos.maciej.codes/common-regex.html)
describes how these patterns become token rules. We don't need a callback or
a new dependency.

Keep the keyword, identifier, punctuation, trivia and error rules, along with
`Token` and `scan`, unchanged. This edit adds a lexical category. It doesn't
add a numeric payload: as with names, `token.range.slice(source)` retrieves
the original spelling. A spelling such as `00.50` remains exactly `00.50`.
Converting it to a runtime number will be a later consumer's job.

## Keep signs and names at their boundaries

Neither `-` nor `+` appears in the number rule. `-12` therefore produces
`Minus` then `Number`; later grammar can treat the minus as a unary operator.
`+3.5` similarly produces `Plus` then `Number`, without making a claim that
unary plus is valid Lox.

The identifier rule still permits digits after a name's first character.
`a2` stays one identifier. In `123abc`, the number ends before `a`, and the
remaining `abc` is an identifier. No separator is needed for the scanner to
find that boundary; the parser will decide whether the sequence is legal.

We aren't adding exponent notation or other numeric formats. This rule covers
Lox's integer and decimal-fraction spellings.

            "1.2.3",
            vec![
                (SyntaxKind::Number, 0, 3),
                (SyntaxKind::Dot, 3, 4),
                (SyntaxKind::Number, 4, 5),
            ],
        ),
        (
            "123abc",
            vec![(SyntaxKind::Number, 0, 3), (SyntaxKind::Identifier, 3, 6)],
        ),
        ("a2", vec![(SyntaxKind::Identifier, 0, 2)]),

        assert_eq!(tokens.len(), expected.len(), "{source}");
        for (token, (kind, start, end)) in tokens.iter().zip(expected) {
            assert_eq!(token.kind, kind, "{source}");
            assert_eq!(
                token.range,
                TextRange::new(TextSize(start), TextSize(end)).unwrap(),
                "{source}"
            );
        }
    }

checks exact kinds and byte ranges for dots, signs and neighboring names.
Each expected entry holds a kind, start and end. `zip` pairs tokens with
those entries; the preceding length assertion ensures neither side can have
unexamined extras. The assertion message identifies the input if a case fails.

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Token {
    pub kind: SyntaxKind,
    pub range: TextRange,
}

pub fn scan(source: &str) -> Vec<Token> {
    let mut tokens = Vec::new();

    for (result, span) in SyntaxKind::lexer(source).spanned() {
        let kind = match result {
            Ok(kind) => kind,
            Err(()) => SyntaxKind::Error,
        };
        let range = TextRange::new(TextSize(span.start), TextSize(span.end))
            .expect("Logos spans are ordered");

        tokens.push(Token { kind, range });
    }

    tokens
}
