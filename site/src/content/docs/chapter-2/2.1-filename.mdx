<p className="book-subtitle">Chapter 2 · Reading Source</p>

Our executable always prints the same greeting. To do something useful with a
Lox program, it first needs to know which source file we want to work on. We’ll
give it a filename in the terminal, then follow that argument into our Rust code.

Start from the [completed Chapter 1](/chapter-1/1.1-first-program/).
The Rust Book’s
[“Accepting Command Line Arguments”](https://doc.rust-lang.org/book/ch12-01-accepting-command-line-arguments.html)
explores the same connection between a terminal command and a Rust program.
Here, we’ll select a single filename.

## Pass an argument to rlox

Open a terminal in **`rlox/`**. If you’re at the project root, enter `cd rlox`
first. With the greeting program still in place, run:

```sh
cargo run -- hello.lox
```

The `--` separates Cargo’s options from the arguments for our executable.
Cargo builds and runs `rlox`, passing `hello.lox` along to it. Our program should
still print:

```text title="Program output before the edit"
Hello from rlox!
```

The argument has reached the process, but our code doesn’t read it yet. The
file doesn’t need to exist for this experiment: we’re going to inspect the name,
then add file reading in the next section.

## Select the filename

Rust’s standard library provides `std::env::args()` to obtain the program’s
arguments. `std` is the standard library, `env` is its environment-related
module, and `args` is the function we’re calling. The `::` separators let us
name it through that path without adding an import.

The function returns an **iterator**: something we can ask for successive
values. The first argument normally identifies the executable itself. In the
command above, the filename follows it. Counting from zero, we want argument
`1`.

The iterator’s `nth(1)` method consumes the first value and returns the next
one. But what if the user didn’t supply a filename? Rust represents that
possibility in the return type: `Option<String>`. It is either `Some(...)`,
containing an owned string, or `None`, meaning no value was available. This
makes the missing-argument case something our code must account for.

For this first version, we’ll use `expect("expected a file")` to obtain the
string when it exists. If the option is `None`, `expect` stops the program with
a panic and includes our message. This is temporary error handling; later in
this chapter, we’ll replace it with a useful usage message and a deliberate
failure exit.

In **`rlox/src/main.rs`**, replace the greeting inside `main`:

```diff title="rlox/src/main.rs · inside main"
 fn main() {
-    println!("Hello from rlox!");
+    let filename = std::env::args().nth(1).expect("expected a file");
+    println!("{filename}");
 }
```

`let` introduces a local binding named `filename`. Rust infers that it holds a
`String` from the expression on the right. The calls beginning with dots form
a chain: obtain the iterator, select the argument, then obtain its string or
panic if it’s missing. Read the chain from left to right to follow that sequence.

The last line uses the same `println!` macro as before. This time, `{filename}`
inside the format string asks it to insert the value of our binding. The
program will print the selected name followed by a newline.

Save the file. Its complete contents should now be:

```rust title="rlox/src/main.rs · complete file"
fn main() {
    let filename = std::env::args().nth(1).expect("expected a file");
    println!("{filename}");
}
```

Run the command again, using `--quiet` before the separator to hide Cargo’s
routine progress messages:

```sh
cargo run --quiet -- hello.lox
```

Expected program output:

```text title="Program output after the edit"
hello.lox
```

`--quiet` is an option for Cargo. `hello.lox` is an argument for `rlox`.
Keeping that boundary clear will matter as our executable gains its own options.

## A name with spaces

A shell usually separates arguments at spaces. Quote a filename containing a
space so it reaches the program as one argument:

```sh
cargo run --quiet -- "my program.lox"
```

The expected output is:

```text title="Program output"
my program.lox
```

The surrounding quotes group the words for the shell; they aren’t part of the
filename received by our program. Without them, `my` and `program.lox` would
arrive as separate arguments, and this version would print only `my`.

In fact, we haven’t implemented any extra-argument validation yet. Try:

```sh
cargo run --quiet -- hello.lox other.lox
```

It should still print `hello.lox`. We selected argument `1` and never asked
whether anything followed it. We’ll tighten that rule when we improve input
errors; for now, this is the actual behavior of the small program we’ve written.

## Leave out the filename

What should happen when `nth(1)` cannot find a value? Predict the result, then
run this **intentional failure**:

```sh
cargo run --quiet --
```

The program should panic and exit unsuccessfully. Among the diagnostic text,
look for the message we supplied:

```text title="Expected panic message · excerpt"
expected a file
```

The compiler let us call `expect`, but that call made a runtime promise: a value
would be present. This input breaks that promise. The panic shows where our
current error handling ends; it isn’t the experience we want someone using a
language tool to have.

Return to a successful run by supplying the argument again:

```sh
cargo run --quiet -- hello.lox
```

The output should be `hello.lox`. No source edits are needed to recover.

`args()` supplies Unicode strings; its
[standard-library documentation](https://doc.rust-lang.org/std/env/fn.args.html)
also describes `args_os()` for operating-system arguments that cannot be
represented that way. Our examples here use Unicode filenames.

We can now choose a source filename from the terminal. The next step is to
open that file and obtain its contents—the text we’ll eventually turn into
tokens, syntax, and running Lox.
