`123` now becomes a tree. For `(123)`, we need to recognize a different
shape: an opening parenthesis, an expression inside it, and the closing
parenthesis. The inner expression might itself begin with `(`.

```text title="An expression rule can lead back to itself"
expression → primary
primary    → NUMBER | "(" expression ")"
```

The `|` separates alternatives. A primary is either a number or a grouped
expression. This grammar has a cycle: an expression can contain another
expression. We'll turn that cycle into method calls, following
[recursive descent in Crafting Interpreters](https://craftinginterpreters.com/parsing-expressions.html#recursive-descent-parsing).

Start from [Section 11.1](/chapter-11/11.1-parse-number/), in the **Rust
workspace directory**. We'll change `parser.rs` and the input list in our
parsed-expression example. Our `Expr::Grouping` variant and prefix printer
already provide the result we need.

## Give recursive calls the same cursor

The local iterator in `parse` was enough for one number. Nested grammar
calls need a cursor that survives a call into an inner expression. We'll
put the cursor and borrowed source in a private `Parser` first, keeping the
number-only behavior unchanged for a checkpoint.

**Complete the following three edits before compiling.** First, insert
this block **after the current public `parse` function and before
`#[cfg(test)]`** in **`rlox/crates/syntax/src/parser.rs`**:

```rust title="rlox/crates/syntax/src/parser.rs · insert parser state and cursor helpers"
struct Parser<'src> {
    source: &'src str,
    tokens: Vec<Token>,
    current: usize,
}

impl<'src> Parser<'src> {
    fn new(source: &'src str) -> Self {
        let mut tokens = scan(source);
        tokens.retain(|token| {
            !matches!(token.kind, SyntaxKind::Whitespace | SyntaxKind::LineComment)
        });
        Self {
            source,
            tokens,
            current: 0,
        }
    }

    fn peek(&self) -> Option<Token> {
        self.tokens.get(self.current).copied()
    }

    fn bump(&mut self) {
        self.current += 1;
    }

    fn error(&self, message: &str) -> ParseError {
        match self.peek() {
            Some(token) => error_at(token, message),
            None => {
                let end = TextSize(self.source.len());
                ParseError {
                    message: message.to_owned(),
                    range: TextRange::new(end, end).expect("ordered EOF range"),
                }
            }
        }
    }
}
```

The parser owns its token vector and current index, but borrows the source.
`Parser<'src>` names the lifetime of that borrowed string; the source must
remain valid while the parser uses it. `impl<'src> Parser<'src>` makes the
same relationship available to the constructor. This annotation doesn't
extend the source's lifetime or copy its contents. See the Rust Book's
[lifetime annotations in structs](https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html#lifetime-annotations-in-struct-definitions).

`retain` removes trivia from this parser-owned vector in place, keeping
other tokens in order. It replaces our filtered iterator's view without
changing `scan` or the tokens' source ranges. The standard library documents
[`Vec::retain`](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.retain).

`peek` observes the current token without advancing. `get` returns `None`
at the end; `copied` copies our small `Token`, whose kind and range already
implement `Copy`. We don't keep a reference into the vector while another
method needs to advance it. `bump` advances after a caller has established
that a token is present. `error` reports that current token or constructs
our existing empty EOF range.

Second, **inside this `impl`, after `new` and before `peek`**, insert the
number rule. It carries over our spelling conversion, then advances past
the number:

```rust title="rlox/crates/syntax/src/parser.rs · insert the number rule"
    fn number(&mut self) -> Result<Expr, ParseError> {
        let token = match self.peek() {
            Some(token) => token,
            None => return Err(self.error("expected a number")),
        };
        if token.kind != SyntaxKind::Number {
            return Err(self.error("expected a number"));
        }

        let spelling = token
            .range
            .slice(self.source)
            .expect("scanner ranges are valid");
        let value = spelling
            .parse::<f64>()
            .map_err(|_| error_at(token, "invalid number"))?;
        self.bump();
        Ok(Expr::Number(value))
    }
```

Each rule takes `&mut self` because it may advance the shared cursor. That
is a temporary mutable borrow for the method call; it doesn't transfer
ownership of the parser. The Rust Book explains
[mutable references](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html#mutable-references).

Third, replace **only the existing public `parse` function** with:

```rust title="rlox/crates/syntax/src/parser.rs · replace the public entry point"
pub fn parse(source: &str) -> Result<Expr, ParseError> {
    let mut parser = Parser::new(source);
    let expr = parser.number()?;
    if parser.peek().is_some() {
        return Err(parser.error("expected end of input"));
    }
    Ok(expr)
}
```

The public function still owns the full-input check. The rule builds a
number; the wrapper rejects any token left over. The return type and
`error_at` helper stay unchanged.

## Let a primary contain another expression

A call for `(123)` should consume `(`, read an inner expression, and then
consume `)`. The inner rule must leave the closing token for its caller.
Calling the public `parse` function recursively would be wrong: its
full-input check would treat that closing token as extra input.

We'll keep that wrapper separate from a private `expression` rule. For
now `expression` delegates to `primary`; later precedence levels will fit
between them.

Parentheses also introduce input-controlled recursion. For this teaching
parser, choose a budget of **64 nested groups**. The entry call starts at
zero; each grouping passes one more to its inner expression. This is a project resource
policy, not a Lox grammar restriction or a measured portable stack capacity.
The boundary example around `1` is only 129 bytes, so we can exercise it
directly while allowing far more nesting than our small examples use. We
will reject a 65th opening parenthesis before entering another level and
test both sides of the boundary. Future recursive grammar forms must be
accounted for when we extend this budget's meaning.

After the imports, before `ParseError`, add:

```rust title="rlox/crates/syntax/src/parser.rs · grouping budget"
const MAX_NESTING: usize = 64;
```

Inside the `Parser` impl, **after `new` and before `number`**, insert:

```rust title="rlox/crates/syntax/src/parser.rs · insert recursive grammar rules"
    fn expression(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        self.primary(nesting)
    }

    fn primary(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        let token = match self.peek() {
            Some(token) => token,
            None => return Err(self.error("expected an expression")),
        };
        match token.kind {
            SyntaxKind::Number => self.number(),
            SyntaxKind::LeftParen => {
                if nesting >= MAX_NESTING {
                    return Err(self.error("expression nesting limit exceeded"));
                }
                self.bump();
                let inner = self.expression(nesting + 1)?;
                match self.peek() {
                    Some(close) if close.kind == SyntaxKind::RightParen => self.bump(),
                    _ => return Err(self.error("expected ')'")),
                }
                Ok(Expr::Grouping(Box::new(inner)))
            }
            _ => Err(self.error("expected an expression")),
        }
    }
```

The number branch reuses our existing number rule. In the grouping branch,
we first check the depth at the opening token, then advance past it. The
inner call borrows the same parser, so its progress remains visible when
it returns. If it returns an error, `?` propagates it without attempting to
invent a child node.

After a successful inner expression, we require `RightParen` and advance
past it. The `if` on that match arm is a **pattern guard**: it accepts the
token only when its kind is the required close. The fallback reports the
current token or EOF. Our shared `error` helper still identifies lexical
errors, even when they appear where we wanted a closing parenthesis.

Only after consuming the close do we wrap the child in
`Expr::Grouping(Box::new(inner))`. Passing `nesting + 1` as an argument
makes the depth belong to that particular nested call. Returning to the
parent automatically resumes its original depth; there is no counter to
repair on an early error return.

## Watch the cursor return to a closing delimiter

For `((123))`, the significant tokens retain these source ranges:

```text title="Cursor progress and grouping results"
[0..1) (   [1..2) (   [2..5) 123   [5..6) )   [6..7) )

outer primary consumes ( at [0..1)
  inner primary consumes ( at [1..2)
    number consumes 123; cursor now points to ) at [5..6)
  inner primary consumes that close → (group 123)
outer primary consumes close at [6..7) → (group (group 123))
public entry finds no remaining token → success
```

Each grouping owns one opening and one closing delimiter. The inner rule
returns while its caller's close is still waiting. With `(123`, the number
returns at EOF instead, and the grouping reports `expected ')'` at `[4, 4)`.
With `()`, the inner expression finds a close where it needed an expression;
that close is the error location.

In **`rlox/crates/syntax/examples/parse_expression.rs`**, replace only the
opening `for source in [...] {` line with this expanded list. Keep the
match and its output code unchanged:

```rust title="rlox/crates/syntax/examples/parse_expression.rs · replace the input list"
    for source in [
        " 123 // note\n",
        "123 456",
        "",
        "é",
        "(123)",
        "((12.5))",
        "( // é\n123 )",
        "()",
        "(123",
        "(123 456)",
        "123)",
    ] {
```

Run the example:

```sh

```

```text title="Number and grouping observations"

"123 456" => expected end of input [4..7)
"" => expected an expression [0..0)
"é" => invalid token [0..2)
"(123)" => (group 123)
"((12.5))" => (group (group 12.5))

"(123" => expected ')' [4..4)
"(123 456)" => expected ')' [5..8)
"123)" => expected end of input [3..4)
```

The grouping rule owns the missing-close error. The public entry owns the
trailing-close error. Both use the same cursor, but their expectations are
different. Repairing `(123` by adding its closing `)` produces the successful
`(123)` case above.

`[64, 65)` is where the next descent would exceed the budget.

use rlox_text::{TextRange, TextSize};

use crate::expr::Expr;
use crate::{SyntaxKind, Token, scan};

const MAX_NESTING: usize = 64;

#[derive(Debug)]
pub struct ParseError {
    pub message: String,
    pub range: TextRange,
}

fn error_at(token: Token, message: &str) -> ParseError {
    let message = if token.kind == SyntaxKind::Error {
        "invalid token"
    } else {
        message
    };
    ParseError {
        message: message.to_owned(),
        range: token.range,
    }
}

pub fn parse(source: &str) -> Result<Expr, ParseError> {
    let mut parser = Parser::new(source);
    let expr = parser.expression(0)?;
    if parser.peek().is_some() {
        return Err(parser.error("expected end of input"));
    }
    Ok(expr)
}

struct Parser<'src> {
    source: &'src str,
    tokens: Vec<Token>,
    current: usize,
}

impl<'src> Parser<'src> {
    fn new(source: &'src str) -> Self {
        let mut tokens = scan(source);
        tokens.retain(|token| {
            !matches!(token.kind, SyntaxKind::Whitespace | SyntaxKind::LineComment)
        });
        Self {
            source,
            tokens,
            current: 0,
        }
    }

    fn expression(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        self.primary(nesting)
    }

    fn primary(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        let token = match self.peek() {
            Some(token) => token,
            None => return Err(self.error("expected an expression")),
        };
        match token.kind {
            SyntaxKind::Number => self.number(),
            SyntaxKind::LeftParen => {
                if nesting >= MAX_NESTING {
                    return Err(self.error("expression nesting limit exceeded"));
                }
                self.bump();
                let inner = self.expression(nesting + 1)?;
                match self.peek() {
                    Some(close) if close.kind == SyntaxKind::RightParen => self.bump(),
                    _ => return Err(self.error("expected ')'")),
                }
                Ok(Expr::Grouping(Box::new(inner)))
            }
            _ => Err(self.error("expected an expression")),
        }
    }

    fn number(&mut self) -> Result<Expr, ParseError> {
        let token = match self.peek() {
            Some(token) => token,
            None => return Err(self.error("expected a number")),
        };
        if token.kind != SyntaxKind::Number {
            return Err(self.error("expected a number"));
        }

        let spelling = token
            .range
            .slice(self.source)
            .expect("scanner ranges are valid");
        let value = spelling
            .parse::<f64>()
            .map_err(|_| error_at(token, "invalid number"))?;
        self.bump();
        Ok(Expr::Number(value))
    }

    fn peek(&self) -> Option<Token> {
        self.tokens.get(self.current).copied()
    }

    fn bump(&mut self) {
        self.current += 1;
    }

    fn error(&self, message: &str) -> ParseError {
        match self.peek() {
            Some(token) => error_at(token, message),
            None => {
                let end = TextSize(self.source.len());
                ParseError {
                    message: message.to_owned(),
                    range: TextRange::new(end, end).expect("ordered EOF range"),
                }
            }
        }
    }
}
