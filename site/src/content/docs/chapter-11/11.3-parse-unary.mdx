<p className="book-subtitle">Chapter 11 · Parsing Expressions by Hand</p>

Our scanner reads `-123` as a minus token followed by a number. The parser
currently stops at that minus: it knows how to begin a number or grouping,
but not an operation. We already have the expression node we want:

```text title="The tree to build for -123"
Unary: Negate
  │ right operand
  ▼
Number: 123
```

A prefix minus needs an operand. That operand might start with another
minus, as in `--123`, or a parenthesis, as in `-(123)`. This gives us one
more recursive grammar rule:

```text title="Add unary expressions between expression and primary"
expression → unary
unary      → "-" unary | primary
primary    → NUMBER | "(" expression ")"
```

The minus branch calls `unary` again, so it can recognize a chain of prefix
operators. Otherwise it falls back to `primary`. This is the arithmetic
subset of the [unary rule in Crafting Interpreters](https://craftinginterpreters.com/parsing-expressions.html#recursive-descent-parsing).

Start from [Section 11.2](/chapter-11/11.2-parse-grouping/), with your terminal
in the **Rust workspace directory**. We'll add this rule to the existing
parser and reuse `UnaryOp::Negate`, `Expr::Unary` and the prefix printer.

## Read the operand before building its parent

In **`rlox/crates/syntax/src/parser.rs`**, extend the expression import:

```diff title="rlox/crates/syntax/src/parser.rs · import the existing unary operator"
-use crate::expr::Expr;
+use crate::expr::{Expr, UnaryOp};
```

Inside the `Parser` impl, **after `expression` and before `primary`**, insert:

```rust title="rlox/crates/syntax/src/parser.rs · insert the unary rule"
    fn unary(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        match self.peek() {
            Some(token) if token.kind == SyntaxKind::Minus => {
                if nesting >= MAX_NESTING {
                    return Err(self.error("expression nesting limit exceeded"));
                }
                self.bump();
                let right = self.unary(nesting + 1)?;
                Ok(Expr::Unary {
                    op: UnaryOp::Negate,
                    right: Box::new(right),
                })
            }
            _ => self.primary(nesting),
        }
    }
```

The guarded arm recognizes the minus token, using the same
[match-guard syntax](https://doc.rust-lang.org/book/ch19-03-pattern-syntax.html#extra-conditionals-with-match-guards)
we used to check a closing parenthesis. After checking the budget, `bump`
consumes the operator. The recursive call then reads its operand from the
same cursor.

That call must return a complete child before we can move it into
`Box::new(right)`. Only then do we construct the parent unary node. If the
operand fails, `?` returns the error unchanged; there is no placeholder node.
The Rust Book explains this form of
[error propagation](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html#propagating-errors).

The fallback arm doesn't advance the cursor. It lets `primary` decide
whether the current token begins a number or a grouping. If it is neither,
that existing rule reports `expected an expression`. At EOF it reports
that expectation at the source end.

In the existing `expression` method, change its delegation:

```diff title="rlox/crates/syntax/src/parser.rs · enter unary before primary"
     fn expression(&mut self, nesting: usize) -> Result<Expr, ParseError> {
-        self.primary(nesting)
+        self.unary(nesting)
     }
```

The public `parse` wrapper still enters `expression(0)` and checks for
leftover input. The grouping rule still calls `expression` for its child,
so it now accepts a leading minus inside parentheses too. No change to
`primary`, `number`, the cursor helpers or the existing tests is needed.

Check the edits together:

```sh
cargo check -p rlox-syntax
cargo test -p rlox-syntax parser::tests
```

The ten existing parser tests should still pass. Numbers and grouping
reach their old rules through the new fallback.

For `--1`, descent first discovers how much input belongs to the operand.
The first minus waits while a second unary call handles the second minus.
The number ends the descent. Returning then builds the inner negation and
finally the outer one. Consuming a minus before recurring is what makes
progress toward that base case.

## Follow a chain back out

For `--123`, both minus tokens are consumed before the number is returned:

```text title="Cursor and return trace for --123"
[0..1) -   [1..2) -   [2..5) 123

unary(0) consumes the first minus
  unary(1) consumes the second minus
    unary(2) delegates to primary; number consumes 123 → 123
  unary(1) wraps that child → (- 123)
unary(0) wraps that child → (- (- 123))
```

The first operator in the source becomes the outer node. We don't fold
the two negations into a number or perform arithmetic while parsing.
Calling `primary` directly after a minus would handle a number but reject
the next minus in a chain; calling `unary` is what admits `--123`.

Grouping remains visible in the tree:

```text title="Which expression owns the grouping?"
-(123) → (- (group 123))
(-123) → (group (- 123))
```

In the first case, the unary operand is a grouped number. In the second,
the grouping's child is a unary expression. Both use the same existing
expression types, connected in different orders.

## Share the depth budget

The new rule uses the same `nesting` argument as grouping. Entering a unary
operand adds one; entering a group adds one. Falling through from unary to
primary adds nothing, because that grammar call hasn't added a tree node.

The limit therefore means **64 grouping or negation nodes combined along
a path to a number**. Sixty-four negations fit; 32 groups around 32
negations fit; 32 groups around 33 negations exceed the same budget. Giving
each rule its own separate allowance would miss that combined nesting.

Keep `MAX_NESTING` and its message unchanged. Both recursive sites check
the argument at their current opening token before descending further.
This extends the project policy from 11.2 without claiming a portable stack
capacity. Binary tree depth will need attention when we introduce it.

    fn shares_the_budget_between_groups_and_negation() {
        let groups = MAX_NESTING / 2;
        let signs = MAX_NESTING - groups;
        let at_limit = format!(
            "{}{}1{}",
            "(".repeat(groups),
            "-".repeat(signs),
            ")".repeat(groups)

            expr.to_prefix(),
            format!(
                "{}{}1{}",
                "(group ".repeat(groups),
                "(- ".repeat(signs),
                ")".repeat(MAX_NESTING)
            )
        );

        let too_deep = format!(
            "{}{}1{}",
            "(".repeat(groups),
            "-".repeat(signs + 1),
            ")".repeat(groups)
        );
        let error = parse(&too_deep).unwrap_err();
        assert_eq!(error.message, "expression nesting limit exceeded");
        assert_eq!(error.range.start().0, MAX_NESTING);
        assert_eq!(error.range.end().0, MAX_NESTING + 1);

The first checks a unary-only path at the boundary and one beyond it. The
second combines grouping and unary paths, so independently counting their
budgets would produce a false success. Its additional minus is at byte 64,
where the next recursive descent would exceed our shared budget. The
existing all-group boundary test remains unchanged.

use rlox_text::{TextRange, TextSize};

use crate::expr::{Expr, UnaryOp};
use crate::{SyntaxKind, Token, scan};

const MAX_NESTING: usize = 64;

#[derive(Debug)]
pub struct ParseError {
    pub message: String,
    pub range: TextRange,
}

fn error_at(token: Token, message: &str) -> ParseError {
    let message = if token.kind == SyntaxKind::Error {
        "invalid token"
    } else {
        message
    };
    ParseError {
        message: message.to_owned(),
        range: token.range,
    }
}

pub fn parse(source: &str) -> Result<Expr, ParseError> {
    let mut parser = Parser::new(source);
    let expr = parser.expression(0)?;
    if parser.peek().is_some() {
        return Err(parser.error("expected end of input"));
    }
    Ok(expr)
}

struct Parser<'src> {
    source: &'src str,
    tokens: Vec<Token>,
    current: usize,
}

impl<'src> Parser<'src> {
    fn new(source: &'src str) -> Self {
        let mut tokens = scan(source);
        tokens.retain(|token| {
            !matches!(token.kind, SyntaxKind::Whitespace | SyntaxKind::LineComment)
        });
        Self {
            source,
            tokens,
            current: 0,
        }
    }

    fn expression(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        self.unary(nesting)
    }

    fn unary(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        match self.peek() {
            Some(token) if token.kind == SyntaxKind::Minus => {
                if nesting >= MAX_NESTING {
                    return Err(self.error("expression nesting limit exceeded"));
                }
                self.bump();
                let right = self.unary(nesting + 1)?;
                Ok(Expr::Unary {
                    op: UnaryOp::Negate,
                    right: Box::new(right),
                })
            }
            _ => self.primary(nesting),
        }
    }

    fn primary(&mut self, nesting: usize) -> Result<Expr, ParseError> {
        let token = match self.peek() {
            Some(token) => token,
            None => return Err(self.error("expected an expression")),
        };
        match token.kind {
            SyntaxKind::Number => self.number(),
            SyntaxKind::LeftParen => {
                if nesting >= MAX_NESTING {
                    return Err(self.error("expression nesting limit exceeded"));
                }
                self.bump();
                let inner = self.expression(nesting + 1)?;
                match self.peek() {
                    Some(close) if close.kind == SyntaxKind::RightParen => self.bump(),
                    _ => return Err(self.error("expected ')'")),
                }
                Ok(Expr::Grouping(Box::new(inner)))
            }
            _ => Err(self.error("expected an expression")),
        }
    }

    fn number(&mut self) -> Result<Expr, ParseError> {
        let token = match self.peek() {
            Some(token) => token,
            None => return Err(self.error("expected a number")),
        };
        if token.kind != SyntaxKind::Number {
            return Err(self.error("expected a number"));
        }

        let spelling = token
            .range
            .slice(self.source)
            .expect("scanner ranges are valid");
        let value = spelling
            .parse::<f64>()
            .map_err(|_| error_at(token, "invalid number"))?;
        self.bump();
        Ok(Expr::Number(value))
    }

    fn peek(&self) -> Option<Token> {
        self.tokens.get(self.current).copied()
    }

    fn bump(&mut self) {
        self.current += 1;
    }

    fn error(&self, message: &str) -> ParseError {
        match self.peek() {
            Some(token) => error_at(token, message),
            None => {
                let end = TextSize(self.source.len());
                ParseError {
                    message: message.to_owned(),
                    range: TextRange::new(end, end).expect("ordered EOF range"),
                }
            }
        }
    }
}
