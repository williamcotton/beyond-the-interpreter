<p className="book-subtitle">Chapter 12 · Building Lossless Trees with Rowan</p>

We now have coordinate types that our scanner and Rowan can share. Let's
use the scanner's tokens to build our first tree. For a number spelled
`001.50`, we will create a `NumberExpr` node containing a `Number` token
whose text is exactly `001.50`. The node gives the token a structural role,
and the token keeps the spelling available for inspection.

Begin with one simple construction rule. Wrap each number token in a
number node and put every other token directly in the root. This gives us
a small tree we can build and read back before asking grammar functions
to choose more elaborate relationships.

Explore these two small sources. Select a tree entry to connect its parent,
text and byte range. `NumberExpr` is a node containing a `Number` token;
its token keeps the original spelling. The root also keeps the surrounding
comments and whitespace.

<LosslessTree client:load />

The comment containing `é` ends at byte 6, and the following number starts
at byte 7. The comment's non-ASCII letter occupies two bytes. The AST's
stored value has neither these positions nor this comment.

We'll build precisely this small shape. Each number token gets a
`NumberExpr` wrapper; all other tokens remain direct root children. This
step stores source without deciding how operators and groups fit together.
For `1 + 2`, it will retain two number nodes and the intervening tokens,
without constructing a binary expression. The existing arithmetic parser
continues to work separately until the concrete parser replaces it.

## Give every kind one declaration

Rowan stores a kind as a small numeric tag, `rowan::SyntaxKind(u16)`. Our
`SyntaxKind` enum gives those tags Lox names. Trees also need node kinds,
starting with `Root` and `NumberExpr`.

We need conversion in both directions. Casting one of our declared enum
values to `u16` is straightforward. Turning an arbitrary integer back into
an enum requires checking that it names a declared variant. A second
handwritten match list could drift from the enum when a kind is added.
Instead, a small local macro will generate both from the same list.

Try expanding the kind-declaration idea for just `Number` on paper. That
one name must appear in the enum, in the conversion that recognizes its
numeric tag, and in the test's list of declared kinds. Adding `NumberExpr`
requires the same three appearances. The macro repeats those mechanical
uses of each supplied name. The scanner's token attributes travel with the
name into the enum, while the conversion code uses the name alone.

Read the expansion below once for a single `$kind`, then imagine repeating
that expansion for every declared kind.

In **`rlox/crates/syntax/src/lib.rs`**, insert this macro after the imports
and before the existing `SyntaxKind` declaration:

```rust title="rlox/crates/syntax/src/lib.rs · insert kind-declaration macro"
macro_rules! syntax_kinds {
    ($( $(#[$attribute:meta])* $kind:ident, )*) => {
        #[derive(Logos, Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
        #[repr(u16)]
        pub enum SyntaxKind {
            $( $(#[$attribute])* $kind, )*
        }

        impl SyntaxKind {
            pub fn into_raw(self) -> rowan::SyntaxKind {
                rowan::SyntaxKind(self as u16)
            }

            pub fn from_raw(raw: rowan::SyntaxKind) -> Option<Self> {
                match raw.0 {
                    $(value if value == Self::$kind as u16 => Some(Self::$kind),)*
                    _ => None,
                }
            }

            #[cfg(test)]
            const ALL: &'static [Self] = &[$(Self::$kind,)*];
        }
    };
}
```

A declarative macro matches Rust source during compilation. In its pattern,
`$kind:ident` captures a variant name and `$attribute:meta` captures an
attribute such as `token("+")`. The outer `$()*` repeats once per variant;
the inner repetition forwards any attributes on that variant to the enum.
The same captured names generate the checked match arms and a test-only
list. See the Rust Book's [declarative macro explanation](https://doc.rust-lang.org/book/ch20-05-macros.html#declarative-macros-for-general-metaprogramming).

`#[repr(u16)]` gives the enum a 16-bit representation. The enum-to-integer
cast stays inside that representation. In the other direction, each match
arm compares the raw value with a known variant's tag; an unknown value
returns `None`. No integer is treated as a Rust enum before that check.
The tags are internal tree labels, not stable serialized identifiers.

Now change just the opening of the existing enum declaration to invoke
the macro, keeping **every existing variant and Logos attribute** in place:

```diff title="rlox/crates/syntax/src/lib.rs · existing kind-list opening"

-pub enum SyntaxKind {
+syntax_kinds! {
     #[token("(")]
     LeftParen,
```

At its end, add the two node kinds after `Error`:

```diff title="rlox/crates/syntax/src/lib.rs · existing kind-list end"
     Error,
+    Root,
+    NumberExpr,
 }
```

The macro now generates `pub enum SyntaxKind`, including its Logos derive.
Existing scanner code still uses that enum. Like `Error`, our node kinds
have no Logos token or regex rule, so scanning never emits them; the tree
builder supplies them. `Ord` and `Hash` are required by Rowan's language
contract. Their derived implementations concern kind identity, not grammar
precedence.

At the end of the **existing `mod tests`**, before its closing brace, add:

```rust title="rlox/crates/syntax/src/lib.rs · append conversion test"
    #[test]
    fn kind_conversion_accepts_only_declared_kinds() {
        for &kind in SyntaxKind::ALL {
            assert_eq!(SyntaxKind::from_raw(kind.into_raw()), Some(kind));
        }
        assert_eq!(SyntaxKind::from_raw(rowan::SyntaxKind(u16::MAX)), None);
    }
```

The test-only `ALL` list comes from the declaration too. This checks that
every declared tag round-trips, while the undeclared maximum tag is rejected.

```rust title="rlox/crates/syntax/src/tree.rs · language and aliases"
use rlox_text::{SourceTooLarge, slice};
use rowan::GreenNodeBuilder;

use crate::{SyntaxKind, scan};

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum LoxLanguage {}

impl rowan::Language for LoxLanguage {
    type Kind = SyntaxKind;

    fn kind_from_raw(raw: rowan::SyntaxKind) -> SyntaxKind {
        SyntaxKind::from_raw(raw).expect("tree contains an unknown Lox kind")
    }

    fn kind_to_raw(kind: SyntaxKind) -> rowan::SyntaxKind {
        kind.into_raw()
    }
}

pub type SyntaxNode = rowan::SyntaxNode<LoxLanguage>;
pub type SyntaxToken = rowan::SyntaxToken<LoxLanguage>;
pub type SyntaxElement = rowan::SyntaxElement<LoxLanguage>;
```

[`Language`](https://docs.rs/rowan/0.17.0/rowan/api/trait.Language.html)
connects Rowan's numeric tags to a language's named kinds. Its associated
`Kind` type is our enum; its two functions use the conversions we just
added. An unknown tag is an invariant failure here: this module only builds
trees from declared kinds. `from_raw` remains a checked `Option` API when
a caller needs to inspect a raw tag.

`LoxLanguage` is an empty enum used as a type marker. We never construct
a value of it. Rowan's generic node/token handles carry that language type,
and the aliases save us from repeating it at every use. An alias doesn't
create another wrapper. These handles still accept any declared Lox node
kind; expression-specific views come later. The Rust Book explains
[associated types](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html#specifying-placeholder-types-in-trait-definitions-with-associated-types)
and [type aliases](https://doc.rust-lang.org/book/ch20-03-advanced-types.html#creating-type-synonyms-with-type-aliases).

### Try the builder without a scanner

The trace above is a small hand-built version of the function we are about
to write. Here are its operations together. This is a reading experiment,
not another required project file; the `SyntaxKind` and `SyntaxNode` names
are the ones we just defined.

```rust title="Reading experiment · build and inspect one number"
let mut builder = rowan::GreenNodeBuilder::new();
builder.start_node(SyntaxKind::Root.into_raw());
builder.start_node(SyntaxKind::NumberExpr.into_raw());
builder.token(SyntaxKind::Number.into_raw(), "12.5");
builder.finish_node(); // NumberExpr
builder.finish_node(); // Root

let green = builder.finish();
let root = SyntaxNode::new_root(green);
let number = root.first_child().expect("number node");
let token = number.first_token().expect("number token");

assert_eq!(number.kind(), SyntaxKind::NumberExpr);
assert_eq!(token.text(), "12.5");
assert_eq!(usize::from(number.text_range().start()), 0);
assert_eq!(usize::from(number.text_range().end()), 4);
assert_eq!(root.to_string(), "12.5");
```

Read this in two passes. The first six calls describe a tree by opening
containers and adding a leaf. The remaining calls navigate the result. No
recursive-descent rule has run, and Rowan has not decided that `12.5` is a
number: we supplied both the kind and the text ourselves. The scanner and
parser will automate those choices.

Before continuing, imagine adding a whitespace token after closing
`NumberExpr` but before closing `Root`. It would become a second root
child, after the number node. `root.children()` would still return just the
number node; `root.children_with_tokens()` would also return the whitespace.
That distinction makes punctuation and trivia accessible without treating
them as expression nodes.

## Put the source into green storage

Rowan separates **green storage** from **red handles**. Green nodes store
kind, children and text lengths; tokens store kind and exact text. A green
node does not store a parent pointer or an absolute source offset.

A red handle supplies that context: a node's parent and its position in a
particular tree. Child offsets follow from the lengths of preceding
siblings. A number token needn't remember that it began at byte 7 in our
example; a positioned handle can calculate that from the earlier trivia.
The colors name these layers, not anything we need to display in an editor.

Append this function to **`tree.rs`**:

```rust title="rlox/crates/syntax/src/tree.rs · append token-tree builder"
pub fn token_tree(source: &str) -> Result<SyntaxNode, SourceTooLarge> {
    let tokens = scan(source)?;
    let mut builder = GreenNodeBuilder::new();
    builder.start_node(SyntaxKind::Root.into_raw());

    for token in tokens {
        let spelling = slice(source, token.range).expect("scanner ranges are valid");
        if token.kind == SyntaxKind::Number {
            builder.start_node(SyntaxKind::NumberExpr.into_raw());
        }
        builder.token(token.kind.into_raw(), spelling);
        if token.kind == SyntaxKind::Number {
            builder.finish_node();
        }
    }

    builder.finish_node();
    let green = builder.finish();
    Ok(SyntaxNode::new_root(green))
}
```

[`GreenNodeBuilder`](https://docs.rs/rowan/0.17.0/rowan/struct.GreenNodeBuilder.html)
collects children for the current node. `start_node` opens a node,
`token` adds a leaf with its exact text, and `finish_node` closes the most
recently opened node. A number opens and closes its own wrapper inside the
root. Every opening has one closing; even an empty source produces a root.

We use the scanner's checked ranges only to select spelling from the
original source. We don't pass those offsets to Rowan. The builder
accumulates token lengths, so preserving *every* token in order produces
the same byte positions. Filtering out comments here would shift every
later location and break source reconstruction.

`finish` consumes the builder and returns the completed green root.
`SyntaxNode::new_root` gives it a positioned red root at offset zero.
Its handles can expose parents, ranges and text while sharing immutable
green storage. This explains the representation; we don't need a tree
cache or incremental editing system to use it.

`scan(source)?` runs before we build anything, preserving 12.1's file-size
failure. An ordinary `Error` token still has valid source bytes, and we
store those bytes like any other token. A tree containing it isn't a claim
that the source is a valid expression.

```sh

```

Immutability also gives Rowan a useful foundation for revised trees:
unchanged green subtrees can be shared rather than edited in place. This
is a capability of the representation, not an automatic incremental parser.
Our functions still scan and build afresh. Choosing a region to reparse and
reusing unaffected structure would require additional logic that we are not
implementing here. For the current lesson, the payoff is already tangible:
we can ask for a node's source text, parent and byte range.

## Inspect text, children and positions

Create **`rlox/crates/syntax/examples/token_tree.rs`**:

```rust title="rlox/crates/syntax/examples/token_tree.rs · complete initial file"
use rlox_syntax::tree::token_tree;

fn main() {
    for source in ["001.50", " // é\n12.5 // end", "@é!"] {
        match token_tree(source) {
            Ok(root) => {
                println!("source: {source:?}");
                println!(
                    "root: {:?} [{}..{})",
                    root.kind(),
                    usize::from(root.text_range().start()),
                    usize::from(root.text_range().end())
                );
                for element in root.children_with_tokens() {
                    println!(
                        "  {:?} [{}..{}) {:?}",
                        element.kind(),
                        usize::from(element.text_range().start()),
                        usize::from(element.text_range().end()),
                        element.to_string()
                    );
                }
                println!("reconstructed: {:?}", root.to_string());
            }
            Err(error) => eprintln!("{error}"),
        }
    }
}
```

`children_with_tokens` visits immediate children in source order. Its items
may be either nodes or tokens. Here, the number wrapper appears as one node
whose text is its token's spelling; trivia and errors appear as tokens.
The ordinary `children` iterator would skip those token children.

Run:

```sh
cargo run -p rlox-syntax --example token_tree
```

For the source with comments, expect:

```text
source: " // é\n12.5 // end"
root: Root [0..18)
  Whitespace [0..1) " "
  LineComment [1..6) "// é"
  Whitespace [6..7) "\n"
  NumberExpr [7..11) "12.5"
  Whitespace [11..12) " "
  LineComment [12..18) "// end"
reconstructed: " // é\n12.5 // end"
```

The number wrapper and its `Number` token cover the same four bytes.
Selecting them in the comparison above changes the parent being inspected,
even though the highlighted source stays the same. For `001.50`, the tree
keeps all six bytes instead of turning them into `1.5`. For `@é!`, the
example should keep both `Error` spellings and the `Bang` token and
reconstruct the original source.

## Check losslessness and relationships

Append this test module to **`rlox/crates/syntax/src/tree.rs`**:

```rust title="rlox/crates/syntax/src/tree.rs · append tests"
#[cfg(test)]
mod tests {
    use super::token_tree;
    use crate::SyntaxKind;

    #[test]
    fn preserves_all_source_even_without_an_expression() {
        for source in ["", "001.50", " // é\n12.5 // end", "@é!", "1 + 2"] {
            let root = token_tree(source).expect("small source");
            assert_eq!(root.kind(), SyntaxKind::Root);
            assert_eq!(root.to_string(), source);
            assert_eq!(usize::from(root.text_range().start()), 0);
            assert_eq!(usize::from(root.text_range().end()), source.len());
            assert!(root.parent().is_none());
        }
    }

    #[test]
    fn positions_number_and_trivia_without_losing_their_relationships() {
        let root = token_tree(" // é\n12.5 // end").expect("small source");
        let number = root.first_child().expect("number node");
        assert_eq!(number.kind(), SyntaxKind::NumberExpr);
        assert_eq!(number.parent(), Some(root.clone()));
        let token = number
            .children_with_tokens()
            .next()
            .expect("number token")
            .into_token()
            .expect("a token child");
        assert_eq!(token.kind(), SyntaxKind::Number);
        assert_eq!(token.text(), "12.5");
        assert_eq!(token.parent(), Some(number.clone()));
        assert_eq!(token.text_range(), number.text_range());
        let children: Vec<_> = root
            .children_with_tokens()
            .map(|element| {
                (
                    element.kind(),
                    usize::from(element.text_range().start()),
                    usize::from(element.text_range().end()),
                )
            })
            .collect();
        assert_eq!(
            children,
            vec![
                (SyntaxKind::Whitespace, 0, 1),
                (SyntaxKind::LineComment, 1, 6),
                (SyntaxKind::Whitespace, 6, 7),
                (SyntaxKind::NumberExpr, 7, 11),
                (SyntaxKind::Whitespace, 11, 12),
                (SyntaxKind::LineComment, 12, 18),
            ]
        );
    }

    #[test]
    fn keeps_invalid_token_spelling() {
        let root = token_tree("@é!").expect("representable source");
        let tokens: Vec<_> = root
            .children_with_tokens()
            .map(|element| {
                let token = element.into_token().expect("no number nodes");
                (
                    token.kind(),
                    token.text().to_owned(),
                    usize::from(token.text_range().start()),
                    usize::from(token.text_range().end()),
                )
            })
            .collect();
        assert_eq!(
            tokens,
            vec![
                (SyntaxKind::Error, "@".to_owned(), 0, 1),
                (SyntaxKind::Error, "é".to_owned(), 1, 3),
                (SyntaxKind::Bang, "!".to_owned(), 3, 4),
            ]
        );
    }
}
```

The first test checks exact reconstruction and root extent, including an
empty source and input our expression parser rejects. The second checks
that positioned trivia and number children match our byte map, and that
the number token has the number node as its parent. The last preserves
invalid token spelling and the two-byte range of `é`.

pub struct Token {

    pub range: TextRange,
}

pub fn scan(source: &str) -> Result<Vec<Token>, SourceTooLarge> {
    checked_size(source.len())?;
    let mut tokens = Vec::new();

    for (result, span) in SyntaxKind::lexer(source).spanned() {
        let kind = match result {
            Ok(kind) => kind,
            Err(()) => SyntaxKind::Error,
        };
        let range = checked_range(
            checked_size(span.start).expect("validated source length"),
            checked_size(span.end).expect("validated source length"),
        )
        .expect("Logos spans are ordered");

        tokens.push(Token { kind, range });
    }

    Ok(tokens)
}

use rowan::GreenNodeBuilder;

use crate::{SyntaxKind, scan};

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum LoxLanguage {}

impl rowan::Language for LoxLanguage {
    type Kind = SyntaxKind;

    fn kind_from_raw(raw: rowan::SyntaxKind) -> SyntaxKind {
        SyntaxKind::from_raw(raw).expect("tree contains an unknown Lox kind")
    }

    fn kind_to_raw(kind: SyntaxKind) -> rowan::SyntaxKind {
        kind.into_raw()
    }
}

pub type SyntaxNode = rowan::SyntaxNode<LoxLanguage>;
pub type SyntaxToken = rowan::SyntaxToken<LoxLanguage>;
pub type SyntaxElement = rowan::SyntaxElement<LoxLanguage>;

pub fn token_tree(source: &str) -> Result<SyntaxNode, SourceTooLarge> {
    let tokens = scan(source)?;
    let mut builder = GreenNodeBuilder::new();
    builder.start_node(SyntaxKind::Root.into_raw());

    for token in tokens {
        let spelling = slice(source, token.range).expect("scanner ranges are valid");
        if token.kind == SyntaxKind::Number {
            builder.start_node(SyntaxKind::NumberExpr.into_raw());
        }
        builder.token(token.kind.into_raw(), spelling);
        if token.kind == SyntaxKind::Number {
            builder.finish_node();
        }
    }

    builder.finish_node();
    let green = builder.finish();
    Ok(SyntaxNode::new_root(green))
}
