<p className="book-subtitle">Chapter 9 · Giving Lox an Editor</p>

Our extension knows how to edit a Lox file, but its words still need display
categories. In `print "var // text";`, the first word is a keyword, while
`var` and `//` inside the quotes belong to a string. Giving everything its
own regex isn't enough: the editor must remember which context it's in.

Start from [Section 9.2](/chapter-9/9.2-editing-rules/), with your terminal in
**`rlox/editors/vscode/`**. We'll add a TextMate grammar, test it through the
real grammar engine, and use its string/comment scopes for pair exclusions.
The Rust scanner stays unchanged.

## Scopes describe display, themes choose colors

TextMate grammars assign **scope names** such as `keyword.control.lox` and
`string.quoted.double.lox` to spans of source. A theme maps those names to
colors and font styles. We contribute scopes, not a fixed palette.

The [VS Code syntax highlight guide](https://code.visualstudio.com/api/language-extensions/syntax-highlight-guide)
explains this division. It also distinguishes TextMate highlighting from
semantic tokens: a pattern can recognize a name's spelling without knowing
which declaration it refers to. Later our Rust analysis and LSP will supply
that kind of information. A `variable.other.lox` scope here doesn't prove
that the name resolves to a variable.

Our Logos scanner remains the authoritative native token stream, including
errors and UTF-8 ranges. A TextMate grammar serves the editor's lexical
display, with state carried from line to line. It isn't another parser or
interpreter, and its scope spans aren't our `SyntaxKind` values or byte ranges.

## Keep quoted text in its own context

From **`rlox/editors/vscode/`**, create the grammar directory:

```sh
mkdir -p syntaxes
```

Create **`syntaxes/lox.tmLanguage.json`** with this complete content:

```json title="rlox/editors/vscode/syntaxes/lox.tmLanguage.json"
{
  "name": "Lox",
  "scopeName": "source.lox",
  "patterns": [
    {
      "include": "#comments"
    },
    {
      "include": "#strings"
    },
    {
      "include": "#keywords"
    },
    {
      "include": "#numbers"
    },
    {
      "include": "#identifiers"
    },
    {
      "include": "#operators"
    },
    {
      "include": "#punctuation"
    }
  ],
  "repository": {
    "comments": {
      "name": "comment.line.double-slash.lox",
      "match": "//.*$"
    },
    "strings": {
      "name": "string.quoted.double.lox",
      "begin": "\"",
      "beginCaptures": {
        "0": {
          "name": "punctuation.definition.string.begin.lox"
        }
      },
      "end": "\"",
      "endCaptures": {
        "0": {
          "name": "punctuation.definition.string.end.lox"
        }
      }
    },
    "keywords": {
      "name": "keyword.control.lox",
      "match": "(?:and|class|else|false|for|fun|if|nil|or|print|return|super|this|true|var|while)(?![A-Za-z0-9_])"
    },
    "numbers": {
      "name": "constant.numeric.lox",
      "match": "[0-9]+(?:\\.[0-9]+)?"
    },
    "identifiers": {
      "name": "variable.other.lox",
      "match": "[A-Za-z_][A-Za-z0-9_]*"
    },
    "operators": {
      "name": "keyword.operator.lox",
      "match": "!=|==|<=|>=|[=<>!+*/-]"
    },
    "punctuation": {
      "name": "punctuation.lox",
      "match": "[(){}.,;]"
    }
  }
}
```

The top-level `patterns` includes rules from `repository`. A `#name` refers
to a rule in this same file. The editor considers the earliest match in the
line; ordering resolves competing rules starting at the same place.

Most rules match one span. A string instead has `begin` and `end` delimiters.
While that context is open, the outer keyword/comment rules don't apply.
The context can remain open across a line break, which is necessary for Lox's
multiline strings. There is no backslash-escape rule: the next quote ends the
string even when preceded by a backslash. The captures give its delimiters
more specific scopes while retaining the surrounding string scope.

The keyword pattern checks that the spelling isn't followed by another ASCII
name character. This keeps `printer` whole. The identifier rule can consume
names such as `_if` from their beginning, before a later keyword match could
start inside them. A preceding number can end immediately before a keyword,
so `123print` receives separate numeric and keyword scopes.

The number, name and operator rules reuse boundaries we've already taught.
Numbers require digits after a fractional dot; signs remain operators. JSON
escapes the regex backslash in the number rule, so `\\.` supplies a literal
dot match. All sixteen keywords and the remaining punctuation are represented.
The `//.*$` comment rule matches only the remainder of the current line.

## Load the contributed grammar in a test

Create **`test/grammar.test.ts`** with the following initial content:

```ts title="rlox/editors/vscode/test/grammar.test.ts · initial file"
import assert from 'node:assert/strict';
import { readFileSync } from 'node:fs';
import path from 'node:path';
import { test } from 'node:test';
import { INITIAL, Registry, parseRawGrammar, type StateStack } from 'vscode-textmate';
import { loadWASM, OnigScanner, OnigString } from 'vscode-oniguruma';

const root = path.resolve(__dirname, '../..');
const grammarPromise = (async () => {
  const manifest = JSON.parse(readFileSync(path.join(root, 'package.json'), 'utf8'));
  const declaration = manifest.contributes.grammars[0];
  assert.equal(declaration.language, 'lox');
  assert.equal(declaration.scopeName, 'source.lox');
  const grammarPath = path.resolve(root, declaration.path);

  const wasm = readFileSync(require.resolve('vscode-oniguruma/release/onig.wasm'));
  await loadWASM(Uint8Array.from(wasm).buffer);
  const registry = new Registry({
    onigLib: Promise.resolve({
      createOnigScanner: (patterns: string[]) => new OnigScanner(patterns),
      createOnigString: (text: string) => new OnigString(text),
    }),
    loadGrammar: async (scope) => scope === declaration.scopeName
      ? parseRawGrammar(readFileSync(grammarPath, 'utf8'), grammarPath)
      : null,
  });
  const grammar = await registry.loadGrammar('source.lox');
  assert.ok(grammar, 'the contributed grammar must load');
  return grammar;
})();

async function scoped(line: string, state: StateStack = INITIAL) {
  const result = (await grammarPromise).tokenizeLine(line, state);
  return {
    state: result.ruleStack,
    tokens: result.tokens.map((token) => ({
      text: line.slice(token.startIndex, Math.min(token.endIndex, line.length)),
      scopes: token.scopes,
    })),
  };
}
```

We read the contribution from the actual manifest, then resolve its grammar
path. A wrong path or root scope should fail this setup rather than leaving
the test pointed at an unrelated hard-coded grammar file.

Oniguruma's regex engine comes as WebAssembly. `require.resolve` locates its
installed binary; `Uint8Array.from(...).buffer` copies exactly those bytes
into an `ArrayBuffer` for `loadWASM`. This is the regex engine, not a Lox
interpreter compiled to WebAssembly.

The registry needs a grammar loader and factories for the regex scanner and
strings. The callbacks provide those pieces. `grammarPromise` starts this
asynchronous setup once; each test awaits the same loaded grammar. The
[Oniguruma project](https://github.com/microsoft/vscode-oniguruma) documents
its WebAssembly loading API.

`scoped` tokenizes one line and returns both scopes and the state needed for
the next line. `INITIAL` means no carried context. TextMate's returned indices
address the JavaScript string, so we use `slice` on that line, not Rust byte
ranges. The `Math.min` clips a possible end-of-line sentinel to the actual
line length. `type StateStack` imports only a TypeScript type for the helper's
state parameter.

## Check exact keywords and longer names

Append this test **at the end of `grammar.test.ts`**:

```ts title="rlox/editors/vscode/test/grammar.test.ts · append word test"
test('keywords leave longer names whole', async () => {
  const words = 'and class else false for fun if nil or print return super this true var while'.split(' ');
  const result = await scoped(words.join(' '));
  assert.deepEqual(
    result.tokens.filter((token) => token.scopes.includes('keyword.control.lox')).map((token) => token.text),
    words,
  );
  for (const name of ['forest', 'printer', 'true_value', '_if', 'Print']) {
    const result = await scoped(name);
    assert.equal(result.tokens[0].text, name);
    assert.ok(result.tokens.every((token) => !token.scopes.includes('keyword.control.lox')));
    assert.ok(result.tokens[0].scopes.includes('variable.other.lox'));
  }
});
```

These assertions check the scope attached to the original text. Looking at a
regex in isolation wouldn't tell us which competing grammar rule won.

## Carry a string across lines

Append these tests **at the end of the same file**:

```ts title="rlox/editors/vscode/test/grammar.test.ts · append string tests"
test('strings carry state across lines and shield comment-like text', async () => {
  const first = await scoped('print "é🦀 //');
  assert.ok(first.tokens.find((token) => token.text === 'é🦀 //')?.scopes.includes('string.quoted.double.lox'));
  assert.ok(first.tokens.every((token) => !token.scopes.includes('comment.line.double-slash.lox')));

  const second = await scoped('var while" print', first.state);
  assert.ok(second.tokens.find((token) => token.text === 'var while')?.scopes.includes('string.quoted.double.lox'));
  assert.ok(second.tokens.find((token) => token.text === 'print')?.scopes.includes('keyword.control.lox'));
});

test('backslashes do not escape quotes and unfinished strings stay open', async () => {
  const closed = await scoped('"a\\"print');
  assert.ok(closed.tokens.find((token) => token.text === 'print')?.scopes.includes('keyword.control.lox'));

  const first = await scoped('"unfinished');
  const second = await scoped('print // still string', first.state);
  assert.ok(second.tokens.every((token) => token.scopes.includes('string.quoted.double.lox')));
});
```

Passing `first.state` is the important part: starting the second line at
`INITIAL` would forget its unfinished string. `var while` and the comment-like
text stay inside the string until the closing quote; the later `print` is a
keyword again. The backslash case checks Lox's lack of escape processing.

An unfinished string can keep its display context open on later lines. Our
native scanner instead returns an `Error` range at EOF. Those observations
serve different jobs: editor coloring can continue while a document is
incomplete, while native inspection reports malformed input. The grammar
doesn't supply compiler diagnostics.

## Check the remaining boundaries

Append these tests **at the end of the same file**:

```ts title="rlox/editors/vscode/test/grammar.test.ts · append boundary tests"
test('numbers leave signs, dots and following names separate', async () => {
  const result = await scoped('-12.5 123. .5 1e3 1.2.3 123print');
  assert.deepEqual(
    result.tokens.filter((token) => token.scopes.includes('constant.numeric.lox')).map((token) => token.text),
    ['12.5', '123', '5', '1', '1.2', '3', '123'],
  );
  assert.ok(result.tokens.find((token) => token.text === '-')?.scopes.includes('keyword.operator.lox'));
  assert.ok(result.tokens.find((token) => token.text === 'e3')?.scopes.includes('variable.other.lox'));
  assert.ok(result.tokens.find((token) => token.text === 'print')?.scopes.includes('keyword.control.lox'));
});

test('line comments stop at the line boundary', async () => {
  const comment = await scoped('// print "text"');
  assert.ok(comment.tokens.every((token) => token.scopes.includes('comment.line.double-slash.lox')));
  const next = await scoped('print != == <= >= / * + - ! = < > (){}.,;', comment.state);
  assert.ok(next.tokens.find((token) => token.text === 'print')?.scopes.includes('keyword.control.lox'));
  assert.deepEqual(
    next.tokens.filter((token) => token.scopes.includes('keyword.operator.lox')).map((token) => token.text),
    ['!=', '==', '<=', '>=', '/', '*', '+', '-', '!', '=', '<', '>'],
  );
  assert.ok(next.tokens.some((token) => token.scopes.includes('punctuation.lox')));
});
```

The cases check that a dot, sign or following name isn't swallowed into the
number, and that comments stop before the next line. We check scopes rather
than theme-specific colors. The native Rust tests still own the scanner's
full lexical contract.

## Use scopes to guide auto-closing

Now the editor can distinguish strings and comments. In
**`language-configuration.json`**, add `notIn` to each of the three existing
`autoClosingPairs` objects:

```diff title="rlox/editors/vscode/language-configuration.json · pair exclusions"
       "open": "{",
-      "close": "}"
+      "close": "}",
+      "notIn": [
+        "string",
+        "comment"
+      ]
```

Make the corresponding additions for the `(` / `)` and quote objects too:

```json title="rlox/editors/vscode/language-configuration.json · resulting autoClosingPairs"
[
  {
    "open": "{",
    "close": "}",
    "notIn": [
      "string",
      "comment"
    ]
  },
  {
    "open": "(",
    "close": ")",
    "notIn": [
      "string",
      "comment"
    ]
  },
  {
    "open": "\"",
    "close": "\"",
    "notIn": [
      "string",
      "comment"
    ]
  }
]
```

`notIn` uses the standard context names `string` and `comment`, not the full
Lox scope names. VS Code derives those contexts from our grammar's scopes,
as described in the [language configuration guide](https://code.visualstudio.com/api/language-extensions/language-configuration-guide#autoclosing).
Keep the surrounding pairs, bracket declarations and indentation rules as
before; scopes don't turn the indentation heuristic into a parser.

Inside **`test/editor.ts`**, append these checks **at the end of `run`, after
the existing indentation check and before the final function brace**:

```ts title="rlox/editors/vscode/test/editor.ts · append scope-aware checks inside run"
const inComment = await openAtEnd('// ');
await vscode.commands.executeCommand('type', { text: '(' });
assert.equal(inComment.document.getText(), '// (');
console.log('EDITOR CHECK: comment scope suppresses auto-closing');

const inString = await openAtEnd('"text ');
await vscode.commands.executeCommand('type', { text: '(' });
assert.equal(inString.document.getText(), '"text (');
console.log('EDITOR CHECK: string scope suppresses auto-closing');
```

A plain opening parenthesis auto-closed in 9.2. These cases must insert only
the opening character because the cursor is inside a comment or string.
They exercise the grammar/configuration connection inside the actual editor,
while preserving the earlier recognition and editing assertions.
